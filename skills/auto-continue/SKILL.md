# Auto-continue

将当前聊天中明确、已获授权的未完成任务交给内置定时调度，默认每 30 分钟回来尝试继续，直到完成或需要用户处理。使用中文与用户沟通，除非用户使用其他语言。

## 入口与授权

- `/auto-continue` 或 `$auto-continue`：为当前任务启用续跑。
- 附加“查看状态”或 `status`：只读查询，不启用或重启任务。
- 附加“停止”或 `stop`：暂停本技能对应的调度；不终止正在运行的工作进程。用户还要求停止当前工作时，另外遵守该要求。
- 普通“继续”只表示当前回合继续。解释技能、安装技能或引用示例，不表示启用自动化。
- 使用当前可用工具定义；通过 `automation_update` 管理调度，通过 `get_usage_limits` 读取额度，通过 `get_goal` 检查 Goal。没有这些能力时说明缺少什么，不假装已安排。

## 找到当前聊天和已有调度

1. 确定当前聊天 ID，优先使用运行环境提供的 `CODEX_THREAD_ID` 或工具明确提供的当前聊天身份。不要按最近聊天、标题相似或目录相同猜测；不能确认时先询问。
2. 在 `$CODEX_HOME/automations/*/automation.toml` 中只读检查已有调度；`CODEX_HOME` 未设置时使用用户目录下 `.codex`。以 `target_thread_id` 和提示正文中的 `auto-continue:v1` 标识共同匹配，排除验收调度 `auto-continue:acceptance:v1`。保留找到的 automation ID，并用工具 `mode: view` 确认实际状态。
3. 每个聊天仅维护一个本技能调度。同一目标重复启用时更新已有调度，不新建。已存在不同目标时说明当前目标并询问是否替换，不静默扩大范围。多个匹配项时只读报告冲突，先明确要管理的那一个。
4. 无匹配项的状态/停止请求只报告“未启用”。不要修改其他技能或用户建立的调度，不直接改写 automation.toml。

## 启用

从当前聊天提取：用户原始目标、可验证的完成标准、当前进度、工作目录和重要约束。只保留足以恢复任务的内容，不复制敏感信息。没有明确未完成目标就询问；已完成则不安排。若当前回合正在执行原任务，先登记调度，再继续原任务，不为了等待调度而提前放弃工作。

检查 Goal。存在明确暂停、blocked、预算受限或额度受限且需要用户恢复的 Goal 时，不通过普通消息、文件修改或私有接口绕过状态；说明需要用户在 Goal 控件中恢复，并暂不启用本技能。已经存在的 active Goal 保持原样，不创建新 Goal，不改变预算。

读取当前额度：

- 优先使用 `rateLimitsByLimitId`，兼容旧的 `rateLimits`；明确 `ordinaryUsageAllowed` 与各窗口的含义。`usedPercent` 是已用百分比，缺失值不是零。
- 仅检查当前任务适用的额度桶；无法确定多个桶中哪一个适用时，不猜测恢复时间。
- 五小时与周额度同时耗尽时，预计恢复时间取相关耗尽窗口的最晚 `resetsAt`，不能只看五小时窗口。
- 时间用当前聊天明确提供的用户时区显示；时区未知时标注 UTC，不猜测本地时间。校验时间是否仍在未来，过期快照不作为确定的恢复时间。
- 可用时安排普通续跑；明确不足时保留定时尝试；数据不可用时报告“恢复时间未知”，不推断已恢复。购买额度、账户切换、充值或重置券不属于此技能。

创建 `kind: heartbeat`、`destination: thread`、`status: ACTIVE` 的原聊天调度，目标明确绑定当前聊天 ID，默认每 30 分钟尝试唤醒。调度规则由 `automation_update` 的当前接口传入，不向用户展示原始 RRULE。不要改用每次新建聊天的 cron 任务。沿用原聊天的模型、推理和权限，不传额外模型覆盖。

重复启用或改动调度时传入已确认的 automation ID，保留其他现有字段。只在工具确认成功后声称“已启用”。回报：绑定目标、每 30 分钟的频率、额度情况/可确定的恢复时间、状态与停止入口。提醒需保持电脑唤醒、应用运行和项目可访问。

## 持久提示

保存可直接理解的中文指令，填入目标和验收标准，不能只存“继续”或只有技能引用。保留如下信息与行为：

> 此任务由 auto-continue:v1 管理，绑定当前聊天。目标：〔具体目标〕。完成标准：〔可验证标准〕。已有进度：〔简短进度〕。工作环境与约束：〔路径和约束〕。
>
> 每次唤醒先检查最新用户指令和任务状态。只推进上述目标；用户对它的后续修正优先。用户取消、替换为无关目标、任务已完成或需要人工处理时，暂停本调度。不要接手后来出现的新任务。
>
> 检查适用额度与 Goal。明确没有可用额度或额度信息不明时不执行实质工作，保留后续调度；不得通过不断重试请求耗尽资源。暂停或预算受限的 Goal 需要用户恢复，不改变其状态。
>
> 额度可用且任务仍获授权时，检查已有文件、修改、执行结果与活动进程，从实际中断处继续完成并验证任务。复用现有运行，不启动重复进程；发送或提交操作之前检查是否已成功，避免重放。权限、输入和不可自行解决的阻塞交回用户，不反复尝试同一步骤。
>
> 每次产生实质进展时，在本聊天保留简短检查点：完成内容、验证结果、剩余工作和下一步。完成标准满足后，通过 automation_update 暂停本调度；不要归档聊天，不改其他调度。暂停失败时明确告知，之后的唤醒仍应先检查完成状态，不重复执行任务。
>
> 正常等待和没有变化时保持安静；仅在完成、实质失败或需要用户处理时报告。

如果工具返回 automation ID，把它记录在当前聊天；后续可以通过本节的聊天 ID 与标识定位。不要杜撰 ID。报告偏好按上面的用户意图保留；用户明确要求静音时才使用工具的 `notificationPolicy: failed_runs_only`，恢复通知时设为 null，不把该设置写成提示正文。调度器自身的失败通知可能仍然出现。

## 每次唤醒与结束

先执行持久提示的状态检查，再工作。只要任务尚未完成且可推进，就沿原范围继续，不把“唤醒成功”当作“任务完成”。额度仍不足时等待下次；因额度问题根本未能启动模型的那次唤醒，技能无法运行任何恢复逻辑，不能声称自己已检测或修复。

遇到用户取消、目标替换、验收完成、需要用户输入/批准、不可自行解决的错误或不可恢复 Goal 状态时，使用 `automation_update` 将对应调度设为 `PAUSED`，保留其原始字段。明确完成与阻塞的区别。无需删除调度或归档聊天。

## 状态与能力边界

状态报告包含：实际启停状态、绑定目标、频率、当前额度信息、可核实的最后执行结果。工具未提供下一次时间或运行结果时直接说明未知。安装存在、调度创建成功、实际唤醒成功、跨真实额度重置成功是四种不同证据，不互相替代。

本技能不注册操作系统服务，不安装第三方工具，不修改 Codex 数据库。它依赖桌面调度器；调度失败后的重试、应用关闭/休眠后的补跑行为都应以实际观察为准。不要承诺恰好在额度恢复时运行或保证无人值守完成。应在额度耗尽前启用；已耗尽时可能连创建调度也无法执行。

## 验证本技能

运行 skill-creator 的 quick_validate.py；检查正常启用、重复启用、额度不足、未知额度、已完成、取消、等待输入和暂停 Goal 的处理是否符合以上规则。

只有用户要求实施验收时，才创建一个 `auto-continue:acceptance:v1` 标识的短时原聊天 heartbeat。验收只读取上下文并回报预先约定的无敏感标记，不执行原任务或新任务。采用调度器支持的有限次数规则；确保存在未来触发时间。已观察到某版本的单次数规则可能因起始时刻已过去而被拒绝；不要报告该失败为创建成功。唤醒后仍通过工具暂停自己的调度并确认状态。验收调度不参与普通启用/停止匹配。未观察到真实唤醒就报告待验证，不用创建成功代替执行成功。不要为测试故意耗尽额度。
